## 1. 背景与目标

### 1.1 背景

国内站 OpenAPI 运行于旧签署系统（pdf-sign3 域）。ePaaS 已完成基础签署能力建设，需将 OpenAPI 流量逐步迁移至 ePaaS。迁移采用**灰度渐进策略**，最终目标为覆盖 **V3 API 基于文件发起（create-by-file）流量的 ≥ 85%**。

### 1.2 迁移硬约束（沿用 F-004 §1.2）

- V3 接口地址、请求/响应格式、错误码必须与旧系统完全一致；差异由 ePaaS 网关代理层吸收，**客户代码零改动**。
- 签署过程中（sign-url 已下发后）不得切换系统路由。
- Webhook 回调字段结构和枚举值必须与旧系统一致。

### 1.3 本方案解决什么

描述**灰度放量的两层闸门（gid + 接口/参数/参数值）、三步节奏、每步参数范围、进阶门槛、自动降级与黑名单机制**。内部验证阶段（M-1 的 C-1~C-7）不在本文档范围，但作为灰度启动前置门槛在 §4 列出。

## 3. 灰度能力模型（核心）

迁移由**两层闸门**组合驱动，先过「gid 大范围」、再过「接口/参数/参数值细粒度」：

```
                          ┌─────────────────────────────────────────────────┐
                          │       第一层：gid 维度灰度（大范围，套 appid）        │
                          │   白名单 / 黑名单 均按 gid 录入（人工 + 内部审批）      │
                          │   ── 一个 gid 下所有 appid 同进同出 ──              │
                          └─────────────────────────────────────────────────┘
                                            │ 白名单 gid 下所有 appid 的请求进入下一层
                                            ▼
                          ┌─────────────────────────────────────────────────┐
                          │       第二层：接口 + 参数 + 参数值 维度灰度           │
                          │   命中「当前步骤已放量范围」→ ePaaS                   │
                          │   未命中（范围外）→ 自动降级（不进入灰度）              │
                          └─────────────────────────────────────────────────┘
```

### 3.1 第一层：gid 维度（大范围控制，套 appid）

控制**哪些客户进入灰度**，是三步放量节奏的「大门」。

> **为什么套 gid**：一个客户（gid，客户/集团标识）下可能对应多个 appid。若仅按 appid 灰度，会导致同一客户的多个 appid 部分进入灰度、部分留在旧系统，造成同一客户流量割裂（数据不一致、跨 appid 流程归属混乱）。因此**第一层以 gid 为录入单位**，保证同一客户的所有 appid 同时进入或同时退出灰度。

| 机制 | 粒度 | 录入单位 | 触发方式 | 说明 |
|------|------|---------|---------|------|
| 白名单 | gid（含其下全部 appid） | gid | 三步逐步扩容 | 录入 gid 后，该 gid 下所有 appid 同时进入灰度 |
| 黑名单 | gid（含其下全部 appid） | gid | 人工维护 + 内部审批 | 特殊客户/大客户 + 接口能力不匹配客户 |

**gid ↔ appid 映射**：灰度系统**已具备**按 gid 解析出其下全部 appid 的能力，映射数据来源于**用户中心**。

### 3.2 第二层：接口 + 参数 + 参数值 维度（细粒度控制 = 自动降级）

> 对应原需求「客户入参不支持参数时，从 ePaaS 签署降级到公有云签署」。
> 灰度系统**已确认具备**「接口 + 参数 + 参数值」三维度灰度能力：三步放量直接通过该能力配置实现，无需新增值级判断逻辑。

**规则**：
- 每步维护一个**「已放量范围」** = 该步允许进入 ePaaS 的 {接口, 参数, 参数值} 集合。
- 白名单 gid 下所有 appid 的每个请求，按此集合逐项判断：
  - 入参**符合**当前步骤已放量范围 → **进入 ePaaS**（灰度承接）；
  - 入参**不符合**（参数不在范围，或参数值不在当前放量值域）→ **自动降级**，该请求不进入灰度、回公有云（旧系统）。
- **三步逐步扩大「已放量范围」**，最终 = 全部 L1 + L2 接口/参数/参数值。

**参数值维度示例**（同一参数的不同值，分步放量）：

| 参数 | L1 值（第一步放量） | L2 值（第二/三步放量） | L3 值（全程降级） |
|------|-------------------|----------------------|-----------------|
| `signFlowConfig.signConfig.signMode` | `NORMAL` | — | `GLOBAL` |
| `signFlowConfig.authConfig.willingnessAuthModes` | `CODE_SMS` `SIGN_PWD` | `PSN_FACE_*` `PSN_MOBILE_FACE_AUTH` | `PSN_AUDIO_VIDEO_*` |
| `signers[].signerType` | `0` `1` `3` | `2`（法定代表人） | — |
| `signers[].signFields[].signFieldType` | `0`（签章区）`2`（日期） | `1`（备注签字区） | — |
| `signers[].signFields[].normalSignFieldConfig.autoSign` | `false` | `true` | — |

**配置维度补充**：gid 下任一 appid 存在 ePaaS 未支持的 **P2 配置（值为非默认值）**时，整体回旧系统（沿用 F-004 §5.1 配置感知能力）。

### 3.3 后置接口特殊说明（不提供自动降级）

- 后置操作接口（`revoke` / `urge` / `delay` / 列表查询 / 签署区增删 / 文件增删 / 附件增删 / 抄送方增删）按 **signFlowId 归属系统**路由。
- **ePaaS 创建的流程，其后置操作锁死在 ePaaS，物理上无法降级回旧系统。**
- 因此后置接口**不参与第二层「参数/参数值」自动降级**；客户在后置接口上不适配时，按**人工黑名单**处理（第一层，gid 维度）。

## 5. 三步放量（逐步扩大「接口 + 参数 + 参数值」范围）

> **三步的本质**：每步扩大两层闸门的范围——
> 1. 第一层：gid 白名单扩容（纳入更多客户，每个 gid 全量 appid 同步进入）；
> 2. 第二层：「已放量范围」扩大（更多接口、参数、参数值进入灰度，不再降级）。

```
前置门槛（P0+P1=62项 + C-1~C-7 + signFlowId归属路由 + gid映射）──────────
     │
     ▼
第一步（L1 参数值范围）  放量 L1 接口 + L1 参数 + L1 值域 + 首批 gid
     │  进阶：日均5000条 + 稳定10天无新增错误
     ▼
第二步（自动签参数值）   扩大 autoSign 参数值域 + 扩容 gid
     │  进阶：日均40000条 + 稳定观察期无新增错误
     ▼
第三步（全量 L1+L2）   扩大到全部 L2 参数值 + 剩余 gid → 达成 85% 目标
     │
     ▼
人工逐步放行黑名单 gid
```

## 6. 降级与黑名单（两层闸门）

| 能力 | 层级 | 粒度 | 触发方式 | 规则 |
|------|------|------|---------|------|
| **自动降级** | 第二层 | 请求级 | 自动（灰度系统内建） | 入参不在「当前步骤已放量范围」（接口+参数+参数值）→ 不进入灰度 |
| **黑名单** | 第一层 | gid 级（含其下全部 appid） | 人工 + 内部审批 | 特殊客户 / 接口能力不匹配 |

### 6.1 自动降级（第二层）

- 灰度系统按「接口 + 参数 + 参数值」指定灰度范围，三步逐步扩大。
- 白名单 gid 下所有 appid 的请求，入参不符合当前步骤范围 → 自动降级回公有云，客户无感，gid 白名单不变。
- L3/L4 长期在范围外，全程自动降级。

### 6.2 黑名单（第一层，gid 维度）

**两个来源（均人工手动 + 内部审批，按 gid 录入）：**

| 来源 | 场景 | 处理 |
|------|------|------|
| A：特殊客户 / 大客户 | 前期默认不进入灰度 | 人工维护，默认黑名单（录入 gid） |
| B：接口能力不匹配 | 客户反馈接口能力不匹配 | 人工手动加入黑名单（录入 gid） |

**放行机制（#10）**：达到第三步目标后，对黑名单 gid **逐户人工评审**，确认其流量参数已在最终范围内、且 ePaaS 能力已支撑后，逐步放行（该 gid 下全部 appid 同步放行）。**不设自动解除。**

## 7. 监控与回滚

### 7.1 核心监控指标

| 维度 | 指标 |
|------|------|
| 流量 | ePaaS 日均承接流程数、各 gid 流量占比、灰度覆盖率（vs 70 万基线） |
| 质量 | 接口错误率（5xx + 业务错误码）、自动签成功率、印章授权失败率 |
| 自动降级 | 降级量、降级原因分布（按接口/参数/参数值归类）——**观测项，反映未放量范围的自然流量** |
| 一致性 | ePaaS vs 旧系统响应 diff、Webhook 字段 diff、signFlowId 归属正确率 |
| 后置操作 | revoke/urge/delay/列表查询在 ePaaS 流程上的成功率（**无法降级，单独盯**） |

### 7.2 回滚机制

| 场景 | 动作 |
|------|------|
| 单个 gid 错误率超阈值 / 致命缺陷 | gid 维度**人工加入黑名单**（内部审批，该 gid 下全部 appid 同步回旧系统） |
| 单接口出现共性缺陷 | 评估是否临时缩小该接口的「已放量范围」，或全局回切 |
| 系统级故障 | 灰度路由全局切回旧系统（保留总开关） |

> 后置操作接口按 signFlowId 归属路由，**无自动降级能力**，缺陷只能人工黑名单或全局回切，需重点盯防。
