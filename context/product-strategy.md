# 产品策略

> **AI 使用说明**：让 AI 在做方案设计和优先级判断时，知道什么该做、什么不该做、什么先做。

---

## 迭代策略原则

### 原则一：向后兼容优先

**实操含义**：
- 任何 V3 API 变更不得破坏已有集成商的存量调用
- 新增参数必须设默认值或设为可选；已有参数不得修改类型、删除或改变语义
- 行为变更（响应结构调整、状态码变化、业务逻辑改动）须走废弃通知流程，给集成商足够迁移时间
- 评估需求时，第一个问题：**是否影响现有调用方？**

### 原则二：合规/法律要求优先

**实操含义**：
- 涉及电子签名法、数据安全法、个人信息保护法等法规要求的需求，优先级自动升为 P0
- 认证方式（实名认证、意愿认证）的变更须先确认合规合法性，再讨论产品方案
- 有合规依据的需求，可绕过常规排期直接推进

---

## 优先级矩阵

| 需求类型 | 优先级 | 判断依据 |
|----------|--------|----------|
| 合规/法律强制要求 | P0 | 法规要求，不做则违规或影响业务合法性 |
| 签署流程核心能力 | P0 | 产品核心价值主张，直接影响集成商主流程 |
| 流程模板核心能力 | P0 | 高频复用场景，影响集成商效率 |
| 向后兼容修复（Bug/Breaking Change） | P0 | 影响存量集成商可用性 |
| 认证授权 / 印章管理 / 消息推送 | P1 | 核心功能支撑模块 |
| 账号与成员管理 | P1 | 企业侧必要管理能力 |
| 订单计费 / 控制台集成 | P2 | 辅助能力，不影响核心签署流程 |
| 体验优化（无功能变更） | P2 | 提升开发者接入效率，非紧急 |

---

## 边界约束

**当前明确不做**：

| 不做的事 | 原因 |
|----------|------|
| V1 / V2 接口迭代 | 旧版本接口已停止演进，统一引导至 V3 |
| SaaS 产品 Web 控制台 UI 改版 | 超出 OpenAPI 场景范围 |
| C 端 App 体验改版 | 超出 OpenAPI 场景范围 |

**范围约束**：本工作区 PRD 仅覆盖 **V3 OpenAPI** 场景；所有 API 设计以 V3 命名规范和架构为准。
